01 / START

현재 가능한 일과 시작 방법

01 → N

같은 입력 흐름

파일 1개, 여러 파일, 하위 폴더를 포함한 폴더를 입력하고 선택한 파일만 분석합니다.

KLARF

원본 결함 이벤트 분석

좌표·bin·영역·방향 집계와 ring / line / local / lift-pin 상태를 제공합니다. 결함 수는 불량 die 수와 다릅니다.

SQLite

결과와 검토 이력 보존

예측 원본, 실행 시도, batch 구성, 검토 revision을 파일형 DB에 보관합니다.

현재 기본 profile은 합성 dummy 데이터 시험용입니다.
실제 KLARF가 파싱되거나 분석이 성공해도 장비 좌표·bin 의미·판정 기준이 검증된 것은 아닙니다. 사내 적용은 먼저 실제 파일·좌표 명세·독립 정답을 확보한 뒤 진행합니다.

앱 실행

다운로드한 프로젝트 루트(README.md와 requirements.txt가 있는 폴더)에서 터미널을 엽니다. 이 문서의 파일 경로와 명령은 모두 그 폴더 기준입니다. 준비된 Python 3.11/3.12 가상환경을 활성화한 경우 바로 실행합니다.

python -m streamlit run wafer/app.py
다른 PC에서 처음 실행할 때: 환경 준비

64-bit Python 3.11 또는 3.12를 설치한 뒤 프로젝트 루트에서 아래 명령을 실행합니다.

python -m venv .venv

Windows PowerShell:

.\.venv\Scripts\Activate.ps1

macOS / Linux:

source .venv/bin/activate

활성화한 환경에 의존성을 설치하고 실행합니다.

python -m pip install -r requirements.txt
python -m pip check
python -m streamlit run wafer/app.py

기존 conda/venv가 준비되어 있으면 해당 환경을 활성화하면 됩니다. 특정 환경 이름이나 사용자 홈 경로는 필요하지 않습니다. Edge 브라우저 시연·E2E는 시스템 Edge가 설치된 Windows 환경을 기준으로 하며 다른 OS의 브라우저 검증은 별도 준비가 필요합니다.

터미널의 Local URL을 엽니다. 기본 주소는 http://localhost:8501이며 사용 중인 포트에 따라 달라집니다. 종료는 서버를 실행한 터미널에서 Ctrl+C입니다.

02 / WORKFLOW

화면 사용 순서

업로드 / 경로→분석 파일 선택→입력 목록 확인→일괄 분석 실행→요약 / 상세보기→검토 / 다운로드
  1. 파일을 준비합니다.왼쪽 여러 파일 선택 또는 폴더 선택(하위 폴더 포함)을 사용합니다. 서버 파일은 또는 KLARF 경로 (한 줄에 하나)에 파일 경로를 입력할 수 있습니다. 업로드와 경로 입력은 목록에 함께 추가됩니다.
  2. 분석할 파일을 선택합니다.분석할 파일에서 선택을 해제하면 이번 분석에서 제외됩니다. 전체 선택 / 전체 제외도 가능합니다. 업로드 전체 삭제는 현재 파일·폴더 업로드, 경로 입력, 결과 화면을 비우며 원본 파일이나 저장 DB를 삭제하지 않습니다.
  3. Profile과 선택 입력을 확인합니다.기본 YAML 경로는 아래 파일입니다. 경로를 비우면 기본값이 복원됩니다. 다른 경로를 지정하면 유지되며, YAML을 별도 업로드한 경우 업로드가 우선합니다. coverage와 SQLite는 필요할 때 지정합니다.
  4. 입력 목록을 확인합니다.입력 목록 확인을 누른 뒤 파일별 상태와 사유를 확인합니다. 현재 서버 확장자 허용 범위는 .klf / .klarf / .txt입니다. 중복·손상·미지원 파일은 별도로 표시됩니다.
  5. 분석을 실행합니다.일괄 분석 실행을 누릅니다. 한 파일의 실패가 다른 파일의 분석을 막지 않습니다. 선택한 파일에 같은 profile과 coverage를 공통 적용합니다. 서로 다른 장비 규약이나 검사 영역은 나누어 실행하세요.
  6. 요약을 보고 상세로 이동합니다.개요, 분석 단위별 표, 유형별 요약, 맵 갤러리를 확인합니다. 상세 조회할 분석 단위에서 파일을 선택하고 상세 맵·검토 화면 열기를 누릅니다. 상세 화면에서 ← 분석 목록으로 돌아가기를 누르면 업로드·선택·결과가 유지됩니다.
  7. 검토와 다운로드를 수행합니다.SQLite를 지정했다면 상세 화면의 검토 폼에서 revision을 저장할 수 있습니다. 목록에서 전체 요약 CSV·유형 CSV·개별 결과 ZIP, 상세에서 JSON·CSV ZIP을 받습니다.

YAML 내용을 바꾸는 방법
위 경로의 파일을 수정·덮어쓴 뒤 다시 분석하면 새 내용을 읽습니다. 입력 목록 확인 뒤 profile이 바뀌면 UI가 최신 profile로 목록을 재검증합니다. 실행 중에는 고정 사본을 사용합니다. coverage 파일만 바꿨다면 입력 목록 확인부터 다시 진행하세요. 업로드한 YAML 사본을 쓰는 경우에는 새 파일을 다시 업로드하거나 업로드를 제거하고 경로를 사용해야 합니다.

상세보기는 분석 당시 결과입니다. 왼쪽 설정 변경만으로 기존 결과가 재계산되지는 않습니다. 파일 선택·입력 설정을 변경하면 목록 화면의 이전 검증·결과는 초기화됩니다.

03 / INTERPRETATION

결과를 읽을 때 지켜야 할 기준

0과 미계산은 다릅니다

0은 실제 0건, null·빈 칸·-는 미계산 또는 해당 없음입니다. 표의 문자열 변환 때문에 None/nan으로 보일 수도 있습니다.

성공은 모든 기능의 확정이 아닙니다

succeeded / valid여도 coverage·노치·점 수가 부족할 수 있습니다. 기능별 calc_status, feature_status, reason을 함께 봅니다.

후보는 원인 판정이 아닙니다

candidate는 보정 전 형상 후보입니다. matched도 규칙 일치이며 공정 원인 확증은 아닙니다. 점수·위험 등급은 제공하지 않습니다.

  • 같은 결함이 여러 유형·영역에 속할 수 있어 유형 수를 단순히 더하면 안 됩니다. 고유 ID 합집합과 유형별 분모를 확인합니다.
  • 엄격 시계방향 집계는 12 sector 합 + center = 포함 결함 수입니다. 경계 허용오차 집계는 인접 sector 양쪽에 세므로 합이 더 클 수 있습니다.
  • no_clear_pattern은 정상 판정이 아닙니다. insufficient_data는 점 수·방향·coverage 등의 근거 부족입니다.
  • 지도 bin 필터와 결과 표 필터는 표시만 바꿉니다. 분석 파일 선택/제외는 실제 분석 대상을 바꿉니다. 갤러리는 맵당 최대 2,000점을 표시하지만 통계에는 전체 점을 사용합니다.
  • 지원되는 좌표 규약 안에서 노치 위치만 누락된 경우 개수·반경 집계는 제공하고 물리 시계방향은 보류합니다. 지원하지 않는 mirror·좌표 규약은 임의 변환하지 않습니다.

04 / PRACTICE

Coverage와 SQLite를 직접 시험하기

A. Coverage: 검사 면적이라는 분모 제공

Coverage는 실제 검사한 영역을 명시하는 JSON 보조 파일입니다. 결함 분포에서 검사 면적을 추정하지 않습니다. 현재는 웨이퍼 중심 원판 full_disk만 지원하고, 반경은 0 < radius_mm ≤ wafer_radius_mm이어야 합니다.

{
  "coverage": {
    "shape": "full_disk",
    "radius_mm": 150,
    "source": "synthetic test only: declared full 150 mm disk"
  }
}
  1. 기본 profile로 klarf_dummy_data/klarf/F01_counts.klarf를 분석합니다. coverage는 비워 두고 면적 보정 밀도가 미상인지 확인합니다.
  2. coverage 경로에 tests/fixtures/coverage/full_disk_150.json을 입력하고 입력 목록 확인 → 일괄 분석 실행을 다시 누릅니다.
  3. 목록의 면적 보정 밀도 표 또는 요약 CSV의 valid_area_mm2, density_per_mm2를 확인합니다. 표가 넓으면 가로로 스크롤하세요.
  4. 상세보기의 공간 집계·판정 상태와 JSON의 result.provenance.coverage, result.radial_density, result.clark_evans를 확인합니다.

B. SQLite: 예측과 검토를 보존하는 파일형 DB

  1. 기존 폴더 아래 새 DB 경로, 예를 들어 프로젝트 루트의 analysis_test.db를 입력합니다. 파일은 자동 생성되지만 부모 폴더는 존재해야 합니다.
  2. F01_counts.klarf와 F01_up.klarf 두 개를 기본 profile·위 coverage로 실행합니다. 성공 2개, 포함 결함 합 16을 확인합니다.
  3. 동일 입력·설정·코드와 같은 DB 경로로 다시 실행합니다. 개요의 저장 결과 재사용 2를 확인합니다. 계산 자체는 다시 수행하며 DB 결과 중복 저장을 막는 방식입니다.
  4. 첫 파일의 상세보기에서 action=confirm, payload={}로 검토 저장을 누릅니다. revision 1, review_status=confirmed를 확인합니다.
  5. 목록으로 돌아가도 결과가 유지됩니다. 같은 분석 키로 다시 열면 검토가 남습니다. profile·coverage·코드 등이 바뀌면 다른 분석 키가 되어 별도 결과로 저장됩니다.

05 / ADAPTATION

사내 데이터 적용 시 무엇을 수정해야 하나요?

YAML 숫자 변경만으로 새로운 장비를 지원할 수 있는 것은 아닙니다. 먼저 입력 문법·좌표 규약이 기존 구현과 같은지 확인한 뒤, 검증된 규약에 맞춰 profile을 작성합니다. 시험 YAML은 남겨 두고 사내 전용 profile을 별도 관리하는 방식을 권장합니다.
